# Workflow Gaps — the registry for gaps in HOW we work

Any agent or orchestrator that hits friction in the multi-agent workflow registers it HERE —
durable and structured, unlike `say "WORKFLOW: ..."` chat messages (which scroll away).

## Hard rules (the structure is not optional)

1. **One row per gap** in the Registry table below. Every column filled — no blanks; use `—`
   only for Next proof on `wont_fix`.
2. **Gap ID**: take `next_free_id` from the YAML header and increment it. Never reuse or
   renumber an ID (including archived ones).
3. **Suggested agent is assignment guidance, not classification.** Use one exact key from
   `tools/agora/agents.json`, based on the harness and capabilities needed to repair the gap.
   Use `human-operator` only when the repair requires an operator-only decision or access.
4. **Registrant provenance is exact.** `Registered by` is the live Agora handle, not a role
   such as `orchestrator` or `claude`; `Registrant ID` is the full Agora agent UUID; and
   `Task/thread` is the registering agent's exact task, thread, or stable external run ID.
   Historical rows that predate these fields say `unknown (legacy)` instead of guessing.
5. **Status** ∈ the YAML `allowed_statuses`. New gaps start `open` (or `blocked` with the
   blocker named in Notes). Only move to `resolved` with EVIDENCE (test, commit, live-verify)
   in the Evidence column.
6. **Evidence is concrete**: file:line, test name, message seq, measured number — never
   "seems to" or "probably".
7. **Link work to gaps**: board tasks addressing a gap carry `--ref workflow:WF-G<n>`;
   `orchestrate reconcile <plan> --root tools/agora` then cross-checks done tasks against
   this registry like any other (`--apply` writes the row update for you).
8. **Registering is cheap and encouraged** — a WORKFLOW: chat message that matters should
   ALSO become a row here. If unsure whether it belongs, register it; `wont_fix` is a valid
   outcome, silent loss is not.
9. **Resolved rows MOVE to the Resolved archive** at the bottom (with their resolution
   evidence) so the Registry shows only live work. Archive rows are retained forever but are
   NOT machine-indexed. Corrections to archived rows go in their Notes.

## Surface notes (planning surfaces)

The two planning surfaces are **distinct** — log friction against the right one:

- **`planmap`** — the roadmap-capture surface at `public/planmap/` (topics.json, health.json,
  session-groups.json, derive scripts; `client.mjs task` refs use `planmap:<topic>/<feature>`).
- **`roadmap`** — the generated node graph under `devtools/roadmap/` (generate-master-roadmap.ts,
  roadmap-derive-structured-doc.ts, and the capability-doc → manifest → generator → UI pipeline).
- **`project-tracker`** — DEPRECATED. Retained only for existing rows and the still-live
  `docs/projects/**/GAPS.md` feature-gap data source (read by `client.mjs --gaps`, served by
  `server.mjs`, parsed by `gapIndex.mjs`). Do NOT tag new gaps with it; use `planmap` or
  `roadmap`. Its data-source retirement is the planning-surface-freshness campaign, not a relabel.
